# 10개 앱의 상업적 가능성 검토

작성일: 2026-11-06. 검토 대상은 각 저장소의 README, 현재 구현 구조와 최근 텍스트 처리·데이터 복구 개선입니다. 실제 유료 구매, 고객 인터뷰, 광고 집행, 현재 경쟁 제품 가격·기능 조사 또는 시장규모 검증은 수행하지 않았습니다. 아래의 고객 반응·지불 의사·획득 경로는 검증할 **가설**이며, 등급은 이 포트폴리오 안의 상대적인 투자 우선순위입니다. 매출 전망이나 법적 적합성 보증이 아닙니다.

## 먼저 내릴 결정

10개를 동시에 유료 출시하면 판매·지원·업데이트 부담도 10개가 됩니다. 먼저 **Stampbook 한 제품으로 실제 구매와 반복 사용을 확인**하고, QuickBill과 QuoteFit은 같은 프리랜서 고객군에서 함께 검증하는 편이 합리적입니다. Shadepad는 개발자 대상 시연이 쉽지만 탐지 신뢰성 검증을 먼저 해야 합니다. Stayline과 Marginlog는 문제의 중요성은 높아도 계산·증거에 대한 신뢰 비용이 커서 초기 매출을 급하게 노릴 제품으로 권하지 않습니다.

| 제품 | 상대 우선순위 | 가장 설득력 있는 가치 | 큰 장애물 | 먼저 할 검증 |
|---|---|---|---|---|
| Stampbook | A | 선불 수업 잔여 횟수·만료·미수금의 반복 관리 | 강사와 수강생 사이의 기록 신뢰 | 강사 5명의 실제 수업 장부 대체 |
| QuickBill | A | 견적부터 청구·부분결제·미수금까지 연결 | 세무 문서로 오인, 강한 대체재 | 프리랜서 5명의 실제 청구 흐름 |
| QuoteFit / App8 | A− | 예상 대비 실제 시간으로 다음 견적 개선 | 기록 입력 습관·적은 표본 | 완료 프로젝트를 가진 5명의 견적 회고 |
| Shadepad | B+ | AI에 붙여넣기 전 로컬 가림·원문 복원 | 탐지 누락·오탐과 보안 신뢰 | 합성 로그로 누락·오탐 검증 후 유료 시연 |
| Quotanest | B | 입력 정리·문서 검사·사용 로그 작업대 | 추정치를 실제 한도로 오인, 수동 입력 | 코딩 사용자 5명의 일주일 사용 |
| PromptVault / App10 | B− | 변수 입력·기본값·복사를 통한 반복 업무 | 메모 앱·텍스트 확장기와의 경쟁 | 특정 직무 템플릿의 반복 사용 |
| Lendnest | C+ | 물품·금전 대여와 부분 상환의 한 장부 | 개인 고객의 낮은 지불 유인 | 장비 대여가 반복되는 소규모 조직 |
| RenewLedger / App9 | C+ | 갱신·체험 종료·구독 비용 가시화 | 수동 갱신 정보 유지, 무료 대안 | 구독이 많은 5명의 실제 정리 |
| Stayline | C, 신뢰 검증 후 재평가 | 여러 사람의 체류 계획 비교 | 입국·세금 판단으로 오인될 위험 | 공식 사례 대조와 전문가 검토 |
| Marginlog | C, 신뢰 검증 후 재평가 | 사건 기록과 자료를 시간순 보고서로 정리 | 증거성·민감정보·데이터 분실 위험 | 전문가가 보고서 활용성을 검토 |

등급 A도 수익성이 입증되었다는 뜻은 아닙니다. 문제 빈도, 절약할 작업, 타깃 명확성, 현재 기능 적합성, 고객 접근성, 지원·신뢰 부담을 함께 고려한 판단입니다.

## 1. Stampbook

**확인된 제품:** 선불 수강권, 출석·보강·취소, 잔여 횟수와 만료, 미수금, 주간 일정, 갱신 안내, 영수증·CSV·잔여 링크가 있습니다. 브라우저 저장을 기본으로 하며 라이선스 확인은 외부 서비스에 연결됩니다. 코드에는 선택적 Supabase 백업 연결도 있습니다. 근거: [README](https://github.com/sangsangbaksa-dev/stampbook/blob/main/README.md), `app/core.js`, `app/app.js`.

- **타깃·문제:** 개인 과외·레슨·코칭 운영자. 여러 학생의 선결제 수업을 메시지와 수기로 대조하는 일을 줄입니다. 반복 수업이 있는 만큼 재사용 이유가 명확합니다.
- **유료 가치·차별화 가설:** 단순 출석표보다 잔여 수업·만료·미수금·보강을 한 흐름에서 확인하고 수강생에게 안내하는 편의. 무료 3개 수강권과 유료 무제한 모델이 구현되어 있으나 실제 결제 전환은 확인하지 않았습니다.
- **대안·획득:** 스프레드시트, 종이 출석표, 캘린더, 학원 관리 서비스가 대안입니다. 강사 커뮤니티에 가짜 학생 데이터로 ‘출석→잔여 안내→재등록’ 1분 시연을 올리고, 허락받은 강사에게 직접 사용성을 조사하는 경로가 적합합니다.
- **비용·운영:** 기본 정적 호스팅 비용보다 라이선스·환불·이용 지원이 중요할 수 있습니다. 학생 이름·출석·결제 정보가 포함되므로 공유 링크 접근 범위, 기기 분실, 백업과 복구를 명확히 안내해야 합니다. Supabase 백업을 제공한다면 사용자별 접근 통제도 검증해야 합니다.
- **출시 전 보완:** 실제 결제·키 활성화·환불 테스트, 지원 연락처, 출석 취소·보강의 실제 운영 사례, 학생 링크에 노출되는 정보 확인. 개인 브라우저 장부를 다중 직원 동시 편집 제품으로 판매하지 않습니다.
- **첫 실험·판정:** 강사 5명에게 2주간 실제 수업을 병행 기록하게 합니다. 3명 이상이 매주 자발적으로 쓰고 2명 이상이 유료 사용 의사를 보이면 다음 실험으로 진행합니다. 이는 내부 의사결정 기준이며 예상 전환율이 아닙니다.

## 2. QuickBill

**확인된 제품:** 견적→청구서 전환, 세금·할인·부분 결제, 연체 안내, 고객 장부, 시간 청구, 문서·시트, CSV와 선택적 클라우드 백업이 있습니다. README의 판매안은 무료 문서 제한과 일회성 $19 라이선스이나, 실제 결제 상품 설정은 별도 검증 대상입니다. 근거: [README](https://github.com/sangsangbaksa-dev/quickbill/blob/main/README.md), `logic.js`, `share.js`, `workspace.js`.

- **타깃·문제:** 혼자 일하는 디자이너·개발자·콘텐츠 제작자. 견적과 청구, 부분 입금과 미수금 확인이 흩어지는 문제를 다룹니다.
- **유료 가치·차별화 가설:** 회계 전반을 배우지 않고 고객별 청구를 끝내는 작업량 절감. 로컬 우선 저장과 다국어 문서는 장점이 될 수 있지만 기능 수 자체가 구매 이유는 아닙니다.
- **대안·획득:** 문서·시트 양식과 기존 청구·회계 서비스. 직무별 견적·청구 예시, 세금 문서와 구분한 안내 콘텐츠, 프리랜서 커뮤니티의 실제 작업 시연으로 접근합니다. 검색 노출은 가설이며 유입을 보장하지 않습니다.
- **비용·운영:** 결제 서비스 수수료, 지원·환불, 클라우드 백업 선택 시 인증·저장 비용과 접근 통제. 일회성 요금으로 장기간 서버 비용을 약속하면 손익이 나빠질 수 있습니다.
- **출시 전 보완:** 세금계산서 발행·세무 신고를 대신하지 않는다는 범위, 국가별 세금·반올림·부분 결제 사례, 원문을 담는 공유 링크, 백업 복원, Supabase 사용자 격리 점검. 오프라인 우회 키를 강한 유료 보안처럼 설명하지 않습니다.
- **첫 실험·판정:** 5명이 기존 방식과 앱에서 같은 실제 견적·부분 입금 업무를 처리하게 하고 소요 시간·수정 횟수·누락을 비교합니다. 비용을 아낀다고 느끼는 기능이 무엇인지 묻고 그 기능을 첫 화면과 판매 설명에 집중합니다.

## 3. QuoteFit / App8

**확인된 제품:** 견적 금액·예상/실제 시간·실질 시급, 카테고리·고객별 편차, 다음 견적 제안, 범위 변경, 템플릿, CSV·백업 기능이 있습니다. 현재 폴더는 App8, 원격 저장소 이름은 QuoteFit입니다. 근거: [README](https://github.com/sangsangbaksa-dev/QuoteFit/blob/main/README.md), `logic.js`.

- **타깃·문제:** 반복 수주가 있지만 작업 시간을 적게 잡아 손해 보는 프리랜서. 과거 견적의 오차를 다음 견적에 반영하도록 돕습니다.
- **유료 가치·차별화 가설:** 시급·범위 변경·고객별 오차를 한 번에 회고하는 구체적 손익 가치. QuickBill 사용자와 겹치므로 별도 구독보다 번들·상위 패키지로 검증할 여지가 큽니다. 현재 유료 상품 연결은 확인되지 않았습니다.
- **대안·획득:** 시간 기록 앱과 스프레드시트. ‘지난 프로젝트를 넣어 다음 견적을 조정하는’ 워크숍·체크리스트를 프리랜서 커뮤니티에서 시험합니다.
- **비용·운영:** 로컬 계산은 서버 부담이 낮지만 고객명·금액·실제 시간의 상업 기밀을 다룹니다. 데이터가 부족할 때의 제안 설명과 정확한 백업이 핵심입니다.
- **출시 전 보완:** 제안 근거인 표본 수와 계산 범위 표시, 통화·세금·원가 포함 범위 안내, 적은 표본·이상치 검증, 결제·환불·지원 체계. 제안을 수익 보장으로 홍보하지 않습니다.
- **첫 실험·판정:** 완료 프로젝트가 최소 5개 있는 프리랜서 5명에게 회고를 시킵니다. 이후 실제 견적에 어떤 근거를 적용했는지 확인합니다. ‘예쁜 차트’ 반응보다 의사결정에 사용했는지를 봅니다.

## 4. Shadepad

**확인된 제품:** 패턴 기반 민감값 가림, 번호 태그, AI 답변 원문 복원, 범주 선택, 사용자 지정 문자열, 선택적 암호화 세션 백업. 탐지는 기기에서 실행하고 AI API를 호출하지 않습니다. 이름·주소 등 자유 텍스트를 포괄 탐지하지 않습니다. 근거: [README](https://github.com/sangsangbaksa-dev/shadepad/blob/main/README.md), `app/core.js`, `app/vault.js`.

- **타깃·문제:** 로그·설정·지원 문의를 AI에 넣는 개발자와 기술 지원 담당자. 붙여넣기 전 민감값을 가리고 답변에서 되돌리는 반복 작업을 줄입니다.
- **유료 가치·차별화 가설:** 단순 마스킹보다 원문 복원과 메모리 처리의 편의. 시연은 쉽지만, 기업용 DLP 또는 모든 개인정보 제거 제품이라고 주장할 단계는 아닙니다.
- **대안·획득:** 수동 치환, 편집기 정규식, 스크립트, 조직의 기존 보안 도구. 합성 로그의 전후 화면과 ‘어떤 정보는 놓치는가’ 문서를 개발자 커뮤니티에 공개하는 방식이 적합합니다.
- **비용·운영:** 모델 호출 비용은 없지만 탐지 규칙 유지·새 토큰 형식·오탐 대응·보안 문의 비용이 생깁니다. 세션 백업은 비밀번호 분실을 복구할 수 없고, 사용자가 복원한 원문을 외부로 복사할 수도 있습니다.
- **출시 전 보완:** 합성 비밀값 회귀 모음, 가림 결과 검토 단계, 원본·키가 로그에 남지 않는지 점검, 보안 제보 경로. 규칙 기반 누락 가능성과 적용 범위를 판매 페이지에서도 같은 수준으로 고지합니다.
- **첫 실험·판정:** 공개·합성 샘플로 범주별 누락·오탐을 측정하고, 개발자 5명이 수동 치환과 비교해 시간을 절약하는지 확인합니다. 실제 고객 비밀을 테스트 서버로 모으지 않습니다.

## 5. Quotanest

**확인된 제품:** 휴리스틱 토큰 추정, 규칙 기반 프롬프트 간결화, 사용 로그 해석, 사용자 입력 한도 예측, AGENTS.md/CLAUDE.md 점검, 이어가기 프롬프트 작성. 공식 한도나 정확한 토큰 수를 조회하는 제품은 아닙니다. 근거: [README](https://github.com/sangsangbaksa-dev/quotanest/blob/main/README.md), `app/core.js`.

- **타깃·문제:** 코딩 도구를 반복 사용하는 개인 개발자. 길어진 입력·지시 문서·작업 재개 맥락을 정리합니다.
- **유료 가치·차별화 가설:** 가벼운 로컬 작업대를 통해 반복 입력을 줄이는 가치. ‘구독 한도를 몇 % 절약한다’는 검증되지 않은 수치를 약속하면 신뢰를 잃습니다. 간결화가 의미를 바꾸지 않는지도 중요한 품질 기준입니다.
- **대안·획득:** 도구 내 사용량 표시, 자체 스크립트, 토크나이저, 메모 앱. 실제 코드 없는 예제로 문서 중복·장황함을 찾는 시연과 공개 회귀 테스트를 활용합니다. 특정 회사의 공식 도구처럼 보이지 않도록 합니다.
- **비용·운영:** 계산 비용은 낮아도 로그 형식 변경과 사용자 지원 부담이 큽니다. 로그에 소스·경로·민감값이 섞일 수 있어 로컬 처리 범위와 백업 내용을 명확히 설명해야 합니다.

## 수익 모델과 실행 순서

1. **상품 하나의 운영을 먼저 완성:** Stampbook의 결제→활성화→사용→백업→환불·지원까지 실제 흐름을 검증합니다. 기능 목록과 예쁜 화면만으로 판매 준비가 끝났다고 보지 않습니다.
2. **같은 고객군으로 확장:** QuickBill과 QuoteFit의 사용자가 겹치는지 조사합니다. 하나의 고객 획득 경로를 재사용할 수 있으면 번들 실험을 하되, 개별 제품의 지불 의사를 먼저 기록합니다.
3. **개발자 도구는 신뢰 자료와 함께:** Shadepad는 합성 데이터 누락·오탐 사례, Quotanest는 의미 보존과 추정 한계를 공개합니다. 모델 호출이 없다는 장점을 비용 절약 수치나 보안 인증처럼 과장하지 않습니다.
4. **신뢰 비용이 큰 두 제품은 별도 트랙:** Stayline과 Marginlog는 전문가·공식 사례 검증 없이 유료 광고부터 확대하지 않습니다.
5. **정리 기준:** 2~4주 실험 후 반복 사용과 지불 의사가 약한 제품은 기능을 더 붙이기보다 무료 도구·번들·템플릿 상품으로 위치를 바꿉니다. 실험 기간은 제안이며 실제 수행 결과가 아닙니다.

### 가격·비용을 정하는 방법

- 현재 README의 가격은 설정 또는 판매안의 근거일 뿐, 결제 성공·환불 정책·세금 처리를 검증한 실제 상품 가격이라는 뜻은 아닙니다. 나머지 앱에 임의의 확정 가격을 붙이지 않았습니다.
- 일회성 가격은 로컬·정적 도구와 잘 맞을 수 있지만 영구 지원·무료 클라우드 동기화를 무제한 약속하지 않습니다. 동기화를 유료로 추가한다면 인증·저장·메일·지원 비용과 고객당 사용량을 먼저 측정합니다.
- 손익은 `실수령 매출 − 결제/세금 처리 비용 − 고객 획득 비용 − 호스팅·저장 비용 − 환불·지원·유지보수 비용`으로 봅니다. 무료 호스팅 구간을 장기 원가 0으로 가정하지 않습니다.
- 가격 실험은 동일한 제품·제공 범위를 명확히 설명하고 실제 구매 의사를 측정합니다. 근거 없는 할인 전 가격, 매출 보장, 공식 제휴 표시는 사용하지 않습니다.

### 공통 출시 조건

사업자·지원 연락처와 판매자 정보, 실제 결제 상품·제품 ID·라이선스 동작, 환불 정책, 데이터와 공유 링크의 노출 범위, 백업·복구, 모바일·키보드 사용성을 확인해야 합니다. 현재의 클라이언트 라이선스 확인은 강한 복제 방지 체계가 아닙니다. 앱의 독립성과 참고한 브랜드의 비제휴 관계를 명확히 하고, 명칭·폰트·이미지 권리 및 판매 지역별 요구사항은 실제 운영자가 확인해야 합니다. 이 문서는 그 확인을 완료했다는 증명서가 아닙니다.

## 확인된 위험과 아직 검증하지 않은 사항

- **관측된 배포 문제:** Lendnest의 round3 main `7aca2fac`에 연결된 Cloudflare 빌드 실패를 확인했습니다. GitHub check output에는 원인 오류가 없으므로 코드·권한·호스팅 설정 중 무엇이 원인인지 단정할 수 없습니다. 실제 판매 링크의 가용성을 확인하는 출시 조건으로 남깁니다. round4 이후 결과는 해당 최신 SHA의 검사로 다시 확인해야 합니다.
- **텍스트 오인식:** `하하하` 미제거, Unicode 조합형 검색 불일치, 일부 CSV·날짜 가져오기 오류는 재현과 회귀 테스트로 수정한 사례입니다. 이것이 모든 입력 형식과 브라우저에서 결함이 없다는 증거는 아닙니다. 향후 가져오기 오류는 원본 보존·명확한 실패 안내·취소 가능성을 기준으로 다뤄야 합니다.
- **유료 잠금의 범위:** 클라이언트 로컬 잠금과 오프라인 대체 키는 강한 복제·우회 방지가 아닙니다. 이를 해결한다며 비밀키를 브라우저 코드에 넣어서는 안 됩니다. 실제 라이선스 제품 ID 제한과 활성화·환불 동작을 각 유료 상품에서 확인해야 합니다. App8·App9·App10의 현재 유료 상품 연결은 이 검토에서 확인되지 않았습니다.
- **선택적 클라우드:** 코드상 Supabase 연결이 있는 QuickBill·Stampbook·Stayline에 해당합니다. 공개 클라이언트 키만으로 보안이 성립하지 않으며, 사용자별 RLS 정책·인증·백업 복원 격리를 실제 서비스에서 확인해야 합니다. 이 보고서는 그 정책을 조회·검증하지 않았습니다. 다른 로컬 전용 앱에 같은 클라우드 위험이 구현되어 있다고 단정하지 않습니다.
- **중대 결함의 구분:** 이 검토만으로 미확인 치명적 버그가 존재한다고 단정하지 않습니다. 확인된 결함의 수정과 아직 검증하지 않은 법률·보안·운영 조건을 분리해서 기록합니다. ‘완성’, ‘준법 보장’, ‘보안 보장’이라는 판매 문구의 근거로 사용할 수 없습니다.
